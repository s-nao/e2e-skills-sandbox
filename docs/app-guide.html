Sample Shop 仕様書

商品の検索から注文までと、店舗管理者向けの管理画面を扱うサンプルショップ（ログイン付き）の動作仕様と、コードを読むときの要点をまとめたものです。E2E テストのスキル（spec / data-check / data-seed / run）を試すための題材です。

第 1 部　動作仕様

全体構成

4 つのコンテナを docker compose up -d で起動します。お客さん向けの画面（web）と店舗管理の画面（admin）は別のアプリで、どちらも /api へのリクエストを Vite が api に転送します。

サービス技術ポート役割
webVue 3 + Vite + vue-router5173画面。カートはブラウザの localStorage に保存
adminVue 3 + Vite + vue-router5174店舗管理の画面（詳細）。web とは別アプリで、独自のログイン画面を持つ
apiFastAPI + SQLAlchemy 2.08000商品・カテゴリ・注文・ログインの API と、店舗管理の API（/api/admin）。在庫の引き当て、セッションの管理
dbPostgreSQL 1655432初回起動時に db/init/*.sql でスキーマと初期データ（開発用ユーザーを含む）を作成

商品の閲覧とカートはログインなしで使えます。注文と注文履歴はログインが必要で、注文はログイン中のユーザーに紐づきます。ユーザー登録の画面はなく、ユーザーは seed（SQL）で作ります。店舗の管理者は users.is_admin = true のユーザーで、別アプリの店舗管理画面（:5174）を使えます。

業務ルール

在庫の表示

在庫数一覧のカード「カートに入れる」「在庫ありのみ」で
0在庫切れ押せない除外
1〜5残りわずか（n 点）押せる表示
6 以上表示なし押せる表示

販売停止（is_active = false）

  • 一覧と検索には出ない（件数にも含まれない）
  • 詳細ページを URL で直接開くと 404 →「商品が見つかりません」
  • 注文に含めると 400 →「商品 {id} は購入できません」

注文

  • 1 回の注文で、1 商品あたりの数量は 1〜99。明細は 1 行以上
  • 在庫が足りない商品が 1 つでもあれば、注文全体を受け付けない（409）。一部だけ注文されることはない
  • 成功すると、各商品の在庫から数量を引く。明細の単価は注文した時点の DB の価格
  • 同時に注文されても在庫がマイナスにならないよう、対象の商品の行をロックしてから確認する
  • ログインが必要（未ログインなら 401）。注文はログイン中のユーザーに紐づき、注文履歴には自分の注文だけが出る

ログインとセッション

項目仕様
方式セッション Cookie。名前は session、HttpOnly・SameSite=Lax。JavaScript からは読めないので、画面は GET /api/auth/me でログイン状態を確かめる
有効期限7 日
保存DB の sessions には、Cookie のトークンそのものではなく SHA-256 のハッシュを保存する。DB が漏れても、そのままセッションを乗っ取れない
ログイン失敗パスワード誤り・存在しないメールアドレス・停止中のユーザーは、すべて 401「メールアドレスまたはパスワードが正しくありません」。どれに当たったかを区別しない
応答時間存在しないユーザーでもダミーのハッシュと照合し、応答時間からユーザーの有無を推測させない。ハッシュの強度は bcrypt の cost 12 にそろえる（下の注意を参照）
停止中users.is_active = false のユーザーはログインできない。既存のセッションも、次のリクエストから無効（401）
ログアウトDB のセッションを削除し、Cookie を消す。カートは残る（ブラウザの localStorage にあるため）
戻り先redirect は / で始まり // で始まらないパスだけを受け付ける。外部サイトを指定されたらトップへ（オープンリダイレクト対策、web/src/auth.ts:43）
セッション切れ注文の API が 401 を返したら、画面をログアウトの状態に切り替え、カートに「ログインしてください」と表示する

開発用ユーザー（db/init/002_seed.sql）

メールアドレスパスワード名前状態
customer@example.compassword123山田 花子ログイン可
inactive@example.compassword123停止 済子停止中
admin@example.comadmin123店舗 管理者ログイン可 管理者（is_admin）

ユーザーを SQL で作るときは crypt('パスワード', gen_salt('bf', 12)) と、cost の 12 を必ず書く。省略すると cost 6 になり、API のダミーの照合（cost 12）と応答時間に約 20 倍の差が出て、存在しないメールアドレスが見分けられてしまう（E2E の性能計測で見つかり、修正済み）。

店舗管理画面

管理者（users.is_admin = true）だけが使える画面で、お客さん向けの web とは別の Vue アプリ（admin/、http://localhost:5174/）です。API は web と共通で、Vite のプロキシで /api を api に転送します。未ログインなら /login へ、一般ユーザーなら /forbidden に移ります。Cookie はポートで分かれないため、5173 でログインしていれば 5174 でも同じセッションでログイン済みになります（逆も同じ）。API も同じ条件で守られ、画面を通さなくても 401 / 403 になります。管理者のアカウントは今は SQL の seed で固定です（admin@example.com）。

画面パス主な動作
商品一覧/products販売停止も含めて新しい順に表示。商品名または SKU で検索。編集・削除。削除の前に確認ダイアログ
商品の登録・編集/products/new、/products/:idSKU（英数字・-・_、40 文字まで）、商品名、説明、カテゴリ、価格、在庫、販売中。保存すると一覧へ戻る
CSV 一括登録/products/importファイルを選ぶと、まず確認だけ行い、登録・変更・削除の件数とエラーを表示。「この内容で反映する」で書き込む
売り上げ/sales日付の範囲（日本時間）で絞り、件数と合計、注文の明細（購入者・商品・数量）を表示。注文ごとに削除できる

商品の削除と販売停止

  • 注文履歴の無い商品は、実際に DB から削除する
  • 注文履歴のある商品は削除できない（409）。過去の注文の表示と売り上げが壊れるため。代わりに「販売中」を外して販売停止にする（お客さん向けの一覧と詳細から消える）

CSV の書式

  • UTF-8。1 行目はヘッダーで、必須の列は sku, name, category, price, stock。任意の列は description, is_active, action
  • sku が無ければ登録、あれば変更。category はカテゴリの名前
  • 任意の列を書かなければ、既存の商品ではその値は変わらない（description と is_active）。登録のときの既定は、説明が空、販売中
  • action 列に delete と書いた行はその商品を削除する。注文履歴のある商品は、普通の削除と同じくエラー
  • エラーが 1 行でもあれば、正しい行も含めて何も反映しない。エラーは「N 行目（sku）: 理由」で表示し、反映ボタンは押せない。1 度に 1,000 行まで

売り上げ

  • 範囲の日付は日本時間で、両端を含む。注文の日時が UTC で前日・翌日にずれる夜間の注文も、日本時間の日付で数える
  • 件数と合計は注文済み（placed）だけ。キャンセル済みは明細には出るが、合計には入らない
  • 明細は新しい順に 200 件まで。それを超えると「truncated」の表示が出る（件数と合計は全件分）
  • 注文の削除は記録の訂正で、在庫は戻さない。明細も一緒に消える。削除の前に確認ダイアログ

第 2 部　コードリーディングの要点

読む順番

データの形 → それを扱う API → 画面、の順に読むと迷いません。全部で 2,000 行ほどです。

  1. db/init/001_schema.sqlテーブルは 6 つ（ユーザー・セッション・カテゴリ・商品・注文・明細）。CHECK 制約（在庫 0 以上など）が DB 側の最後の防衛線になっている
  2. api/app/models.py → schemas.pymodels は DB の行、schemas は API の入出力。入力のバリデーション（数量 1〜99 など）は schemas にある
  3. api/app/auth.py → main.pyauth.py はログインと、ログイン必須の API に付ける依存関係 CurrentUser。main.py は残りの API で、一覧の検索条件の組み立て（55 行目〜）と、注文の在庫引き当て（101 行目〜）が中心。管理者向けの API は admin.py にまとめてある
  4. web/src/api.ts → auth.ts → cart.ts → main.ts画面から API を呼ぶ窓口、ログイン状態、カートの状態。main.ts はルーティングと、ログインが必要な画面のガード
  5. web/src/pages/ProductListPage.vue → CartPage.vueURL を状態として扱う一覧と、注文を送るカート。ほかの画面はこの 2 つの縮小版
  6. admin/src/店舗管理の別アプリ。構成は web と同じ（main.ts・App.vue・pages/）。管理画面を触るときだけ読めばよい
  7. e2e/ と .claude/skills/アプリが分かってから。spec → data → tests → reports の順にファイルを追う。テストの共通部品は e2e/support/、画面の操作は e2e/pages/

ログインの流れ

sequenceDiagram
  participant U as ブラウザ
  participant R as ルーター（main.ts）
  participant A as FastAPI（auth.py）
  participant D as PostgreSQL
  U->>R: /orders を開く
  R->>A: GET /api/auth/me（初回だけ）
  A-->>R: 401（未ログイン）
  R-->>U: /login?redirect=/orders へ
  U->>A: POST /api/auth/login {email, password}
  A->>D: users を検索
  A->>A: bcrypt で照合（ユーザーがいなければダミーと照合）
  A->>D: INSERT sessions（トークンの SHA-256）
  A-->>U: 200 ユーザー + Set-Cookie: session
  U->>R: safeRedirect(redirect) → /orders
  R-->>U: 注文履歴を表示

以降のリクエストには Cookie が自動で付き、ログイン必須の API は CurrentUser（api/app/auth.py:36）で Cookie のトークンをハッシュにして sessions と照合します。期限切れ・停止中のユーザーは 401 です。

注文 1 件の流れ

sequenceDiagram
  participant U as ブラウザ（CartPage）
  participant V as Vite（/api を転送）
  participant A as FastAPI create_order
  participant D as PostgreSQL
  U->>V: POST /api/orders {items}（Cookie 付き）
  V->>A: 転送

  A->>D: SELECT products ... FOR UPDATE OF products
  Note over A,D: 対象の商品の行をロック

  A->>D: UPDATE stock / INSERT orders, order_items

エラーで HTTPException を投げると、コミットされないままセッションが閉じるので、在庫の減算も含めてすべて取り消されます。

ファイル別の要点

注文の在庫引き当てapi/app/main.py:101
  • with_for_update(of=Product) の of= は必須。商品とカテゴリは外部結合で読み込む設定のため、これが無いと PostgreSQL が「外部結合の NULL になりうる側はロックできない」とエラーにする
  • 同じ商品が明細に 2 回出ても、同じ product オブジェクトから在庫を引くので、合計で判定される
  • order.total は API で計算する。画面から送られた金額は使わない
  • 引数に user: CurrentUser を書くだけでログイン必須になる。注文の user_id もここから取り、画面からは受け取らない
商品一覧の検索api/app/main.py:46
  • 条件をリストに積んで where(*conditions) に渡す。件数と一覧で同じ条件を使い回す
  • 並び順は SORT_COLUMNS（27 行目）の辞書。同じ値のときの順序がぶれないよう、必ず id を第 2 キーにしている（ページ送りで重複・抜けが出ないため）
  • ILIKE '%…%' は通常のインデックスが効かない。大量データでの性能測定の対象
ログインの APIapi/app/auth.py
  • BCRYPT_COST = 12（18 行目）と、ユーザーを作る SQL の gen_salt('bf', 12) は必ずそろえる。ずれると応答時間でユーザーの有無が分かる
  • 失敗の条件（ユーザーがいない・パスワード誤り・停止中）を 1 つの if にまとめ、同じ 401 を返す（61 行目）
  • Cookie の secure=False はローカルの http 用。https で公開するときは True にする
画面のログイン状態とガードweb/src/auth.ts / main.ts:26
  • ログイン状態はモジュールの最上位の reactive に持つ。カートと同じく全画面で共有する
  • ensureLoaded() は /api/auth/me を最初の 1 回だけ呼ぶ。ルーターのガードから毎回呼んでも、2 回目以降は待たない
  • ルートの meta.requiresAuth でログインが必要な画面、meta.guestOnly で未ログイン専用の画面（ログイン画面）を表す。管理画面（admin/src/main.ts）は同じ作りのガードに、管理者だけの画面を表す meta.requiresAdmin（一般ユーザーは /forbidden へ）が加わる。auth.ts・api.ts は web からコピーしたもので、共有モジュールにはしていない
  • 戻り先は必ず safeRedirect() を通す。E2E の login S8 が、このガードを外すと失敗することを確認済み
URL を状態として扱う一覧画面web/src/pages/ProductListPage.vue:50
  • 「検索」ボタンは API を直接呼ばず、URL のクエリを書き換えるだけ（search()）
  • route.query を watch して API を呼ぶ（67 行目）。戻る・進む・リロードでも同じ経路を通る
  • 既定値（新着順、1 ページ目）は URL に出さない。?q=… の形が E2E のテストで使われている
カートの状態web/src/cart.ts
  • モジュールの最上位にある reactive 配列を全画面で共有する（Pinia は使っていない）
  • 変更されるたびに localStorage に保存する（18 行目）。商品オブジェクトを丸ごと保存するので、価格や在庫は追加した時点のまま
  • テンプレートで cart.total.value と書くのは、cart がただのオブジェクトで、中の computed が自動では展開されないため
API の呼び出しとエラーweb/src/api.ts:42
  • 全 API がここを通る。ApiError にステータスコードを持たせ、画面側は 401 / 404 などで表示を分ける
  • toSearchParams は空文字と false を送らない。in_stock=false を明示的に送る手段はない
店舗管理の APIapi/app/admin.py
  • APIRouter(dependencies=[Depends(require_admin)]) で、ルーター全体を管理者だけにする。require_admin は CurrentUser（未ログインは 401）に is_admin の確認（403）を足したもの
  • 商品の削除は、注文明細に載っているかを先に調べて 409 にする。外部キーのエラーに頼らない
  • CSV の取り込みは、全行を検証して「登録・変更・削除の予定」に分け、エラーが無く dry_run でもないときだけ、最後にまとめて書き込む（全件反映か全件不反映）
  • 売り上げの日付は timezone('Asia/Tokyo', created_at) を日付にして比較する。件数と合計の集計と、明細の取得は別のクエリ
  • 注文の削除は delete(Order) の 1 文。明細は ON DELETE CASCADE で消える
テスト用の目印web/src/pages/*.vue、admin/src/pages/*.vue
  • 操作・確認の対象には data-testid を付ける。商品カードとカートの行には data-sku もある
  • 文言や CSS クラスを変えても E2E が壊れないように、テストは data-testid だけを使う。画面を直すときは、この属性を消さない
