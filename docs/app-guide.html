Sample Shop 仕様書

商品の検索から注文までを扱うサンプルショップの動作仕様と、コードを読むときの要点をまとめたものです。E2E テストのスキル（spec / data-check / data-seed / run）を試すための題材です。

第 1 部　動作仕様

全体構成

3 つのコンテナを docker compose up -d で起動します。ブラウザは web にだけアクセスし、/api へのリクエストは Vite が api に転送します。

サービス技術ポート役割
webVue 3 + Vite + vue-router5173画面。カートはブラウザの localStorage に保存
apiFastAPI + SQLAlchemy 2.08000商品・カテゴリ・注文の API。在庫の引き当て
dbPostgreSQL 1655432初回起動時に db/init/*.sql でスキーマと初期データを作成

認証はありません。注文は顧客のメールアドレスで識別します。

画面と遷移

画面パス主な動作
商品一覧/ 商品名の部分一致検索、カテゴリ、「在庫ありのみ」、並び順（新着・価格の安い順・高い順・名前順）。12 件ごとにページ分け。検索条件は URL のクエリに入るので、リロードや共有で同じ結果を再現できる
商品詳細/products/:id 説明・価格・在庫数を表示。数量を指定してカートに追加。在庫 0 なら数量欄とボタンの代わりに「在庫切れ」。販売停止の商品は「商品が見つかりません」
カート/cart 数量の変更（0 で削除）、合計金額。メールアドレスを入れて注文。成功するとカートを空にして完了画面へ。失敗したらエラーを表示し、カートは残す
注文完了/orders/complete/:id 注文番号を表示。注文履歴へのリンク（メールアドレスを引き継ぐ）
注文履歴/orders?email= メールアドレスで注文を新しい順に一覧表示。明細と合計

業務ルール

在庫の表示

在庫数一覧のカード「カートに入れる」「在庫ありのみ」で
0在庫切れ押せない除外
1〜5残りわずか（n 点）押せる表示
6 以上表示なし押せる表示

販売停止（is_active = false）

  • 一覧と検索には出ない（件数にも含まれない）
  • 詳細ページを URL で直接開くと 404 →「商品が見つかりません」
  • 注文に含めると 400 →「商品 {id} は購入できません」

注文

  • 1 回の注文で、1 商品あたりの数量は 1〜99。明細は 1 行以上
  • 在庫が足りない商品が 1 つでもあれば、注文全体を受け付けない（409）。一部だけ注文されることはない
  • 成功すると、各商品の在庫から数量を引く。明細の単価は注文した時点の DB の価格
  • 同時に注文されても在庫がマイナスにならないよう、対象の商品の行をロックしてから確認する
  • メールアドレスは形式をチェックする。.test などの予約ドメインは拒否される（422）

API

メソッドパスパラメータ・本文応答
GET/api/health—{"status":"ok"}
GET/api/categories—カテゴリの配列（id 順）
GET/api/products q 商品名の部分一致 / category_id / in_stock / sort = newest・price_asc・price_desc・name / page（1〜）/ page_size（1〜100、既定 12） {items, total, page, page_size}
GET/api/products/{id}—商品 1 件。販売停止・存在しない場合は 404
POST/api/orders {customer_email, items: [{product_id, quantity}]} 201 で注文。400 / 409 / 422 は エラーを参照
GET/api/orderscustomer_email（必須）その顧客の注文を新しい順に

起動中は http://localhost:8000/docs で Swagger UI を見られます（FastAPI が自動生成）。

第 2 部　コードリーディングの要点

読む順番

データの形 → それを扱う API → 画面、の順に読むと迷いません。全部で 1,000 行ほどです。

  1. db/init/001_schema.sqlテーブルは 4 つだけ。CHECK 制約（在庫 0 以上など）が DB 側の最後の防衛線になっている
  2. api/app/models.py → schemas.pymodels は DB の行、schemas は API の入出力。入力のバリデーション（数量 1〜99、メール形式）は schemas にある
  3. api/app/main.py全 API が 1 ファイルに入っている。一覧の検索条件の組み立て（51 行目〜）と、注文の在庫引き当て（97 行目〜）が中心
  4. web/src/api.ts → cart.ts画面から API を呼ぶ窓口と、カートの状態。画面のコードはこの 2 つを使うだけ
  5. web/src/pages/ProductListPage.vue → CartPage.vueURL を状態として扱う一覧と、注文を送るカート。ほかの画面はこの 2 つの縮小版
  6. e2e/ と .claude/skills/アプリが分かってから。spec → data → tests → reports の順にファイルを追う

注文 1 件の流れ

sequenceDiagram
  participant U as ブラウザ（CartPage）
  participant V as Vite（/api を転送）
  participant A as FastAPI create_order
  participant D as PostgreSQL
  U->>V: POST /api/orders {email, items}
  V->>A: 転送
  A->>A: OrderIn で検証（失敗なら 422）
  A->>D: SELECT products ... FOR UPDATE OF products
  Note over A,D: 対象の商品の行をロック
  A->>A: 販売中か（400）・在庫は足りるか（409）
  A->>D: UPDATE stock / INSERT orders, order_items
  A->>D: COMMIT（ロック解放）
  A-->>U: 201 OrderOut
  U->>U: カートを空にして /orders/complete/:id へ

エラーで HTTPException を投げると、コミットされないままセッションが閉じるので、在庫の減算も含めてすべて取り消されます。

ファイル別の要点

注文の在庫引き当てapi/app/main.py:97
  • with_for_update(of=Product) の of= は必須。商品とカテゴリは外部結合で読み込む設定のため、これが無いと PostgreSQL が「外部結合の NULL になりうる側はロックできない」とエラーにする
  • 同じ商品が明細に 2 回出ても、同じ product オブジェクトから在庫を引くので、合計で判定される
  • order.total は API で計算する。画面から送られた金額は使わない
商品一覧の検索api/app/main.py:41
  • 条件をリストに積んで where(*conditions) に渡す。件数と一覧で同じ条件を使い回す
  • 並び順は SORT_COLUMNS（23 行目）の辞書。同じ値のときの順序がぶれないよう、必ず id を第 2 キーにしている（ページ送りで重複・抜けが出ないため）
  • ILIKE '%…%' は通常のインデックスが効かない。大量データでの性能測定の対象
URL を状態として扱う一覧画面web/src/pages/ProductListPage.vue:50
  • 「検索」ボタンは API を直接呼ばず、URL のクエリを書き換えるだけ（search()）
  • route.query を watch して API を呼ぶ（67 行目）。戻る・進む・リロードでも同じ経路を通る
  • 既定値（新着順、1 ページ目）は URL に出さない。?q=… の形が E2E のテストで使われている
カートの状態web/src/cart.ts
  • モジュールの最上位にある reactive 配列を全画面で共有する（Pinia は使っていない）
  • 変更されるたびに localStorage に保存する（18 行目）。商品オブジェクトを丸ごと保存するので、価格や在庫は追加した時点のまま
  • テンプレートで cart.total.value と書くのは、cart がただのオブジェクトで、中の computed が自動では展開されないため
API の呼び出しとエラーweb/src/api.ts:41
  • 全 API がここを通る。ApiError にステータスコードを持たせ、画面側は 404 などで表示を分ける
  • toSearchParams は空文字と false を送らない。in_stock=false を明示的に送る手段はない
テスト用の目印web/src/pages/*.vue
  • 操作・確認の対象には data-testid を付ける。商品カードとカートの行には data-sku もある
  • 文言や CSS クラスを変えても E2E が壊れないように、テストは data-testid だけを使う。画面を直すときは、この属性を消さない

既知の注意点

内容影響場所
カートは追加した時点の価格を表示するが、注文は DB の現在の価格で計算する要仕様決定 価格が変わると、カートの合計と実際の請求額がずれるcart.ts
422 のとき、どの項目が悪いのかが画面に出ないUX ブラウザの検証は通るメールアドレスで起きるapi.ts:41
