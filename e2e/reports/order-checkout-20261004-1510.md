## 失敗の分析

今回の実行はすべて成功。直前の 1 回目（15:08）で S4 / S5 が失敗したので、その記録を残す。

| シナリオ | 分類 | 根拠 | 対応 |
|---|---|---|---|
| S4, S5 | 仕様 | D6 のメールアドレス `e2e-oc@example.test` を、API の `EmailStr` が予約ドメインとして 422 で拒否した | spec の D6 を `e2e-oc@example.com` に変更。e2e-spec スキルに「メールは example.com を使う」というルールを追加 |

副次的に見つかった点（実装・要相談）:
- ブラウザの `type=email` の検証は通るが API が 422 で拒否するメールアドレスを入れると、画面には「入力内容を確認してください」としか表示されず、どの項目が悪いのかわからない。

## 性能の所見

- すべての API が 50ms 未満で、500ms を超えたリクエストはなし。
- 最も遅いのは `POST /api/orders`（48ms）。在庫の行ロック（`SELECT ... FOR UPDATE`）とコミットを含むため妥当。
- 今回のデータ量（商品 15 件）では、検索の性能は評価できない。`name ILIKE '%…%'` はインデックスが効かない検索なので、大量データでの測定は `product-search` の spec で `E2E-PERF-` のデータ（数万件）を作って行うのがよい。
