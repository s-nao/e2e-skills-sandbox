# E2E テスト仕様の策定

機能の仕様をソースコードから読み取り、**後続のスキルが機械的に読める形**でテスト仕様を書く。
このスキルの成果物は `e2e/specs/<feature>.md` の 1 ファイルだけ。DB への接続・データ作成・テスト実行はしない。

## 入力

- `<feature>`: kebab-case の機能名（例: `order-checkout`, `product-search`）。指定がなければユーザーの依頼文から決めて伝える。
- 対象の範囲（画面・ユースケース）。曖昧なら、コードを読んだうえで「この範囲で書きます」と宣言して進める。質問で止めない。

## 手順

1. **仕様を読む**（推測で書かない）
   - 画面: `web/src/pages/*.vue`（`data-testid` と表示文言を拾う）
   - API: `api/app/main.py`（バリデーション、エラーの条件とメッセージ、ステータスコード）
   - DB: `db/init/001_schema.sql`（制約、`is_active` などの状態を表す列）
2. **シナリオを洗い出す**。正常系だけで終わらせず、以下の観点を一度は検討する（該当しないものは書かなくてよい）:
   - 正常系の主経路
   - 境界値（在庫ちょうど・0件・ページ境界・最大数量）
   - データの状態による表示の違い（在庫切れ、残りわずか、販売停止＝非表示）
   - API エラー時の画面表示（400 / 404 / 409）
   - 操作後の DB の状態（在庫が減る、注文が作られる）
3. **前提データを定義する**。シナリオが依存するデータは、既存のデータに頼らずすべて `data_requirements` に書く。
   - 識別子（SKU、メールアドレス、カテゴリ名）は必ず `data_prefix` で始める。後続のスキルはこのプレフィックスで作成と削除を行う。
   - 値はアプリのバリデーションを通るものにする。API のスキーマ（`api/app/schemas.py`）を見て確認する。
     - メールアドレスは `<prefix 小文字>@example.com` を使う。`.test` / `.localhost` などの予約ドメインは `EmailStr` に拒否される（422）。
   - 他の機能の spec と衝突しないよう、`data_prefix` は機能ごとにユニークにする（`E2E-<機能の略称>-`）。既存の spec を `grep data_prefix e2e/specs/` で確認する。
4. テンプレート [template.md](template.md) の形式で `e2e/specs/<feature>.md` を書く。既にある場合は、差分を説明してから更新する。
5. 最後に、シナリオ数・前提データ数・**仕様として未確定の点**（コードから判断できなかったもの）を短く報告する。

## 書き方のルール

- シナリオ ID は `S1, S2, ...`、データ ID は `D1, D2, ...`。テストコードとレポートはこの ID で対応を取るので、**既存の ID は振り直さない**（削除したら欠番にする）。
- 期待結果は「画面」と「DB」に分けて書く。画面は `data-testid` と文言で、DB はテーブルと列で、検証できる粒度にする。
  - ✗「正しく表示される」 → ○「`sold-out-badge` に『在庫切れ』と表示され、`add-to-cart` が disabled」
- `mode` は `auto`（Playwright で自動化する）か `manual`（ブラウザで人／Claude が目視確認する。見た目の崩れなど）。基本は `auto`。
- `perf` を付けたシナリオは、e2e-run で API とページの応答時間を重点的に報告する。
